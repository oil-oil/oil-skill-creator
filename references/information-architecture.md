# 信息架构、Token 与弱模型可读性

## 每类内容只放一处

| 层级 | 唯一职责 |
| --- | --- |
| frontmatter | 什么时候触发、什么时候不触发，以及必要的兼容条件 |
| `SKILL.md` | 模式、顺序、决策、分支、停止条件和资源读取时机 |
| `references/` | 特定阶段才需要的清单、数据格式、解释和平台细节 |
| `scripts/` | 确定、重复、可验证的执行 |
| `assets/` | 可复用的页面、样式、静态模板和其他非指令资源 |
| `README.md` | 面向人的价值、安装、配置、使用和边界 |
| 外部 workspace | 输出、反馈、对比报告、Review 和版本比较 |

Agent 只读取 `SKILL.md` 时，就应该能够选择正确路径，不需要先读完所有参考资料。`SKILL.md` 不复制详细检查表和数据格式；参考资料不再解释触发条件；README 不复制 Agent 的内部流程。

## 文件拆分判断

只在以下情况新增或拆分文件：

- **阶段与模式专用**：内容只在某个模式、阶段、平台或框架使用；
- **互斥工作流解耦**：一份参考资料中包含两个目标相反或互斥的子任务（例如“优化 UI 视觉锁定流程”与“改流程与做新功能锁定视觉”）。同一个任务的 Agent 只需要其中一套上下文，强行合并会导致每次执行都加载无关且相反的约束规则，污染模型注意力并浪费 Token。此时必须拆分成独立文件，并在总览中做一级意图分流；
- **重型独立资产与结构骨架抽离**：大篇幅的骨架模板表、大型对照表、枚举字典等，如果属于主流程特定分支下的独立重型产物，应抽离为子文件，让主流程保持轻量干练；
- **程序独立执行**：程序可以直接执行而不需要加载源码；
- **模板与页面独立维护**：可复用页面或静态模板需要独立维护、预览或原样复制；
- **程序需要独立回归测试**；
- **主文件不拆分就无法保持清楚的分支和停止条件**。

### 什么时候不应该拆分（反向判断）

- **全局字典与综合审查清单**：例如视觉语言（字体、色彩、空间、细节、克制），这些要素在界面设计或终审中互相关联、同时生效。如果过度拆碎为多个微型文件（如单独的 `color.md`、`spacing.md`），会导致 Agent 在单次任务中发起多次连续 tool-call 往返，打碎全局上下文且容易漏看。此类高内聚字典应保持单文件一体化，通过顶部目录（TOC）解决寻址；
- **短小且强相关的线性步骤**（< 100 行）：拆碎只会增加目录碎片和路由跳转成本；
- **不要为了形式完整创建空目录**：没有明确读取入口、执行入口或用户用途的资源，补上入口或者删除。

### 拆分时的工程纪律

1. **原样无损搬运（Zero Logic Loss）**：拆分是信息架构分层，不是重写规则；必须保证原文字句、示例与约束 100% 完整迁移，严禁在搬运过程中随意删减原则；
2. **双向路由闭环**：
   - 父文件保留简要概述，并在对应位置放置明确的跳转链接；
   - 顶层入口（如 `SKILL.md` 或评审协议）允许对意图明确的任务一步直接寻址到拆分后的子文件；
   - 子文件顶部或引言中提供回链，指明上级上下文。

## 篇幅梯度与重构信号

单文件不是越短越好，也不是越长越全。按以下梯度评估篇幅：

| 层级 / 类型 | 推荐篇幅 | 职责与要求 |
| --- | --- | --- |
| `SKILL.md` 主流程 | 100～150 行 | 模式选择、分支路由、核心顺序与停止条件，不塞入长表格与具体检查项 |
| 常规阶段参考资料（`references/`） | 50～150 行 | 单个特定任务或阶段的完整规则，处于模型单次阅读最佳舒适区 |
| 综合字典 / 评审手册 | 150～250 行 | 高内聚、全案综合自查字典（如视觉规范、评审协议），**超过 200 行必须配置目录导航（TOC）** |
| 超过 250～300 行 | ⚠️ 触发重构审计 | 检查是否混杂了互斥工作流或可抽离的独立重型表格，优先做职责剥离 |

## 目录导航（TOC）时机与规范

目录导航（TOC）为长文件提供锚点寻址能力，便于模型按需切片阅读（slice 查阅）或直接定位目标章节。

### 何时增加 TOC

- **超过 200 行的长参考资料**：单次通读成本较高，必须在顶部提供 Markdown 锚点目录（校验器在超过 300 行无目录时报 warning）；
- **多分支或字典型参考资料**：包含 4 个以上独立二级标题、供 Agent 针对性按需查阅的文件；
- **包含长流程走查表与多维度归因表的文件**：方便模型在执行走查时快速跳转到目标计数表或归因表。

### 何时不需要 TOC

- **`SKILL.md` 主文件**：通常不加 TOC。它应严格控制在 100~150 行内，依靠顶层的模式选择表与二级标题即可一屏通览；
- **短小参考资料（< 150 行）**：结构一目了然，加 TOC 反而增加冗余行数；
- **纯线性简短协议或单组件规格**（30~80 行）。

### TOC 书写规范

1. **位置**：置于文件一级标题之下、引言/摘要段落之前或紧随其后；
2. **标题格式**：使用 `## 目录导航` 或 `## 目录`（与校验器正则 `^#{1,3}\s+(?:目录|table of contents|contents)\s*$` 保持匹配）；
3. **锚点格式**：使用标准 Markdown 列表与内部锚点链接 `- [章节名称](#章节锚点)`；
4. **锚点对齐**：锚点命名严格对齐标题文本（全小写、空格转连字符、特殊标点剔除），确保点击与语义寻址完全有效。

## Token 开销

拆分文件不会自动节省 Token。只有入口清楚、按需读取，并且同一内容没有重复说明时，分层才有价值。

评估 Token 时同时看输入上下文、工具输出和返工次数，不能只看 SKILL.md 字数。脚本输出默认简洁，详细诊断写入文件或通过 `--json` 请求。

更短不一定更省 Token。能减少探索、错误和返工的程序，即使增加少量说明，也可能降低总成本。

## 写给能力较弱的模型

- 一条指令只包含一个主要动作。
- 明确动作主体、输入、输出和停止条件。
- 把分支和禁止项写在对应步骤旁。
- 同一概念始终使用同一个名称。
- 控制标题深度和列表嵌套，避免多层跳转。
- 不依赖“如上”“照旧”等隐含指代。
- 示例使用最小安全默认值，不展示会造成错误默认的完整配置。
- 程序返回明确状态和下一步，不让模型解析冗长日志。

短并不等于易懂。删除条件、主体或输出会增加猜测和返工；重复完整规则也会让模型不知道哪一份有效。

## 静态复杂度检查

`scripts/validate_skill.py` 检查：

- SKILL.md 行数、章节、段落、标题和列表深度；
- references 是否能从 SKILL.md 到达；
- 大型 reference 是否提供目录；
- 根目录是否堆放职责不明的 Markdown；
- Markdown 文档之间的长段精确或近似重复（换了说法的同一条规则查不出来，需要人工核对）；
- 当前目录可读取的常见文本、源码和配置中的具体用户目录、常见密钥格式、私钥块与可疑明文凭据赋值；
- `.env`、`credentials.json`、私钥文件等不应进入 Skill 的高风险凭据文件；
- 评估数据格式和文档的大致 Token 规模。

这些指标只能发现理解风险。程序无法证明某个模型会选对模式或做出正确语义判断。

## 弱模型试跑

使用计划支持的最低能力模型，在不提供作者上下文的情况下独立运行：

1. 一个完整主流程；
2. 一个容易走错的整改或停止分支；
3. 一个容易混淆但不应触发的任务。

检查它是否选择正确模式、只读取所需资源、调用既定脚本、没有重复实现程序逻辑，并在应该停止的位置停止。失败时先改入口、命名、分支位置或程序接口，不要立即追加更多解释。

如果弱模型不在支持范围，README 和 compatibility 应明确说明，不要为了宣称兼容而无限扩写 Skill。
