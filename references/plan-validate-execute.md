# 高风险操作的计划、校验与执行

批量修改、破坏性操作、复杂校验或失败代价较高的任务，先生成可机器检查的计划，再决定是否执行。普通单次、可逆且低风险的操作不必增加这一层。

## 固定顺序

1. **生成计划**：只读取输入，把拟执行操作写入工作区的 `plan.json`，不修改目标文件，不写入密钥或无关个人数据。
2. **程序校验**：检查 schema、操作 ID、目标范围、重复或冲突操作及前置条件；领域规则由目标 Skill 的程序验证，不让 Agent 目测代替。
3. **Dry-run**：展示将发生的变化和无法执行的项目。计划无效、目标越界或前置状态不符时保持零写入。
4. **用户授权**：说明影响并取得批准，记录计划摘要。批准后计划发生变化，必须重新校验、dry-run 和授权。
5. **执行与验证**：程序执行已批准的操作，逐项检查输出；失败时保留已完成的有效结果和明确错误。
6. **记录与恢复**：把每项状态写入独立的 `run-state.json`，采用临时文件加原子替换。恢复只处理未完成项，已验证成功的操作不得重复执行。

## 计划与状态分离

批准后的计划保持不变，运行状态另存。计划至少包含稳定 ID、动作、目标和可验证的前置条件，例如：

```json
{
  "schema_version": 1,
  "operations": [
    {
      "id": "operation-1",
      "action": "update",
      "target": "relative/path",
      "preconditions": {"sha256": "原文件摘要"}
    }
  ]
}
```

字段可按业务扩展，但不能用自由文本描述代替程序能检查的动作、目标和条件。`run-state.json` 至少记录计划摘要、每项状态、输出证据和错误；不把运行状态回写进已批准计划。

## 验收要求

- 无效计划、重复 ID、冲突目标和不匹配的前置条件均在写入前被拒绝。
- 只有校验和 dry-run 通过且用户批准后才能执行；绕过任一入口都不能写入。
- 部分失败后可以从真实状态恢复，重复运行不会重复已成功操作。
- 用一个正常主流程和至少一个失败分支做端到端测试，检查目标文件而不只检查函数返回值。

这里规定目标 Skill 的设计与验收契约。不同业务的计划 schema、校验器和执行器由目标 Skill 实现，不使用声称适用于所有业务的通用执行器。
