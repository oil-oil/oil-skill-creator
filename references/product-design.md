# Skill 产品设计

## 先判断价值

一个 Skill 至少应当改善以下一项：

- 普通 Agent 经常遗漏关键步骤；
- 同一流程反复发生，每次都在重新摸索；
- 输出需要稳定格式、文件或验证；
- 依赖、配置、权限和失败后的替代方法复杂；
- 需要把个人经验整理成可重复使用的判断方法；
- 需要明确的人机协作节点。

如果只是一次任务、简单提醒或普通 Agent 已能稳定完成，优先使用短文档、模板或独立脚本。Skill 不是默认答案。

## 创建前需要明确的内容

创建前先回答下面的问题。

| 项目 | 要回答的问题 |
| --- | --- |
| 用户 | 谁会在什么环境中使用 |
| 问题 | 哪个重复问题值得被解决 |
| 当前做法 | 不使用 Skill 时哪里不稳定或低效 |
| 预期改善 | 使用后能看到或测量到什么变化 |
| 输入 | 用户需要提供什么 |
| 输出 | 最终交付什么，放在哪里 |
| 边界 | 明确不做什么，交给谁处理 |
| 风险 | 权限、隐私、覆盖、成本和平台限制 |
| 类型 | 客观型、主观型或混合型 |

不要把这张表机械写进每个 Skill。它用于设计决策，只有真正影响使用的内容才进入发布文档。

## 首次使用

默认静默完成能够自动发现、风险低并且可以撤销的准备工作。只有确实缺少用户决定时才询问。

| 行为 | 默认处理 |
| --- | --- |
| 检测操作系统、命令、版本、目录和已有配置 | 静默执行 |
| 创建无冲突的工作目录和缓存 | 自动执行 |
| 读取已有偏好并复用 | 自动执行 |
| 迁移配置且能保留原文件 | 自动执行并汇报 |
| 登录、输入密钥、安装系统软件 | 先说明影响并询问 |
| 覆盖、删除、上传、发布或外部写入 | 必须获得授权 |
| 主观方向会显著改变结果 | 集中询问一次 |

静默不是隐藏。完成后用一句话说明自动完成了什么；失败时说明停在哪一步。

## 阶段完成后的下一步

流程分几个阶段的 Skill，做完一个阶段、交出一部分结果时，在回复末尾列出接下来可以做的事。用户不必了解整套流程，也知道还能往哪走。可选的加深、扩展和代价高的步骤都放进这份清单，由用户来选：Agent 不默认执行，也不为此另开一轮专门询问。

- 最多三条，按推荐顺序排，第一条标“推荐”。只列当前状态下真能做、和本次任务有关的事，不把整套流程列一遍，也不列已经做过的。
- 每条写清做完能得到什么、要付出什么：多花的时间、多耗的 Token、会改动或覆盖哪些文件、要不要调用付费服务。代价没实测过就用粗略的说法，不编数字。
- 用用户的语言和说法，不出现 Skill 内部的步骤编号、文件名和术语。
- 每条带编号，用户回复编号就能选。宿主有选项按钮时可以改成按钮，没有时纯文字也能用。
- 以下情况不列：小改动；本轮本身停在确认点，要问的就是下一步；用户已经说了接下来做什么；无人值守，没有人读。

```text
**接下来可以做**
1. 深度检查（推荐）：请一位独立评审逐项复核，问题会找得更全，要多花一些时间。
2. 出英文版：沿用同样的结构翻译，几分钟。
3. 导出 PDF：在同目录新建文件，不改原稿。

回复编号就行，也可以直接说想怎么改。
```

写进 Skill 时，在交付规则里放一张短表：每个阶段完成后有哪些候选的下一步、各自的代价。Agent 按当前状态从表里挑，不临时编新步骤。

## Agent 与程序的边界

优先程序化的信号：

- 输入输出能被明确描述；
- 同样输入应产生同样结果；
- 每次都必须执行；
- 能用明确结果判断成功或失败；
- 漏做会造成较大损失；
- 多个执行者正在重复实现同一逻辑。

保留给 Agent 的信号：

- 需要理解用户真正想解决的问题；
- 多种策略都合理，需要结合上下文选择；
- 需要语义、审美或编辑判断；
- 例外情况无法穷举；
- 必须与用户协商取舍。

规则固定时由程序执行；需要理解语义或权衡时由 Agent 判断。不要让 Agent 逐条复述脚本内部流程，也不要把主观判断写成看似确定的代码。

## 流程而非规则树

Skill 应提供一条可适应上下文的工作流，而不是枚举越来越多的具体情况。

- 写清阶段目标、输入输出、判断依据、必要分支、恢复与停止条件。
- 只有分支有限、条件客观、处理稳定时，才固化为程序或决策表。
- 需要语义、策略或审美判断时，给出原则和证据要求，让 Agent 结合上下文选择。
- 新问题先寻找已有流程缺口，不为单次失败添加产品名、固定措辞、特殊路径或一次性例外。
- 当规则持续增加却不能提升真实结果时，回退到更简单的流程并重新评估。

## 高风险与批量操作

批量修改、破坏性操作、复杂校验或失败代价较高的任务，按 [计划、校验与执行](plan-validate-execute.md) 设计：先生成无写入的结构化计划，程序校验并 dry-run，授权后执行和验证，再用独立运行状态支持不重复的恢复。无效计划不得修改目标，计划批准后发生变化必须重新授权。

## 大型产物

产物很长不代表一定要拆分。出现以下情况时，才考虑分段生成：

- 一次生成经常失败、遗漏或前后不一致；
- 修改局部内容需要重写整个产物；
- 产物存在稳定、相对独立的组成部分；
- 最终组合可以由程序确定完成。

采用分段生成时：

1. 先定义片段边界、输入输出和稳定标识；
2. 让每个片段能够独立生成、检查和重做；
3. 尽早保存可用的中间产物；
4. 用脚本验证并组装最终产物；
5. 局部修改只重做受影响的片段。

不要按固定行数机械拆分。组成部分彼此强依赖时，使用固定骨架和内容插槽保持整体一致，不要强行切成任意小块。

## 可复用操作页面

用户需要设置多项关联配置、反复预览调整，或者必须进行主观确认时，考虑随 Skill 提供可复用的配置页、编辑器或预览页。

- 页面读取稳定的配置文件或 manifest，不依赖 Agent 临时拼接数据；
- 程序负责启动页面、加载数据、保存结果和检查保存状态；
- Agent 负责说明入口，并在用户完成操作后继续流程；
- 页面和数据分开维护，不要让 Agent 每次重新生成页面；
- 简单选择继续使用对话或配置文件，不要为了形式完整而增加页面。

优先使用本地、可重复启动的页面。确实依赖特定平台界面时，在兼容性中说明，并提供可行的替代路径。
